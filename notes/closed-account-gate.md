# Closed-account gate: one admission boundary for every Account method

Design chain for the closed-account bullet of the wave 10 to 16 residue in
`notes/bugs.md`. Sparred and agreed; links 1 and 2 built, links 3 and 4 not yet.

## Problem

After `Account::close()`, providers disagree about what a later call does:

- Google wraps every `AccountFuture` method in `shutdown_future` (refuse with
  `AccountClosed` before the request, `Transport(Network)` plus `InFlight` if
  close lands mid-flight); streams end silently.
- IMAP refuses explicitly only in send, draft send, raw blob fetch and polling
  EXAMINE. Everything else reaches the pool, which answers
  `TransportFailure::Closed` -> `Transport(Network)` "IMAP connection closed":
  a retryable network error for an account the user removed.
- Graph and JMAP gate only push registration. CalDAV and CardDAV gate nothing
  (`close()` only ends `scope_lifecycle_stream`).

The yardstick: a user who removed an account expects its work to stop. Every
new call refuses uniformly with `AccountClosed` (terminal `Cancelled`) before
I/O, never a transport error, never a silent success.

## Shapes considered

1. Per-provider gates in every method. Six crates times about ninety methods,
   each a place to forget; this is how the current gaps arose.
2. Chokepoint gating (net request builder, IMAP pool checkout, DAV
   `dispatch_once`). Rejected in the spar on concrete bypasses: CalDAV
   `discover_cursor_scopes` yields from cached URLs with no dispatch; the IMAP
   ManageSieve leg opens its own connection outside the pool; local validation
   and inherited `Unsupported` defaults complete before any transport; DAV
   inventory materialises batches up front so closing mid-stream stops no
   output; and a request that passed a boolean check can still dispatch after
   close while it waits on rate admission, a connection or a token. Net's
   builder is also too early: retries re-attempt without a new builder.
3. **Chosen: a shared wrapper in bifrost-types with generated forwarding,**
   backed by one lifecycle/admission implementation. Provider transport gates
   stay as a second boundary.

## Design (as built in link 1)

- `bifrost_types::ClosingAccount<A: ?Sized>` (`crates/types/src/closing.rs`)
  wraps any provider; `ClosingAccount::wrap(Arc<dyn Account>)` returns the
  erased gate. Its `Account` impl is generated by the attribute macro
  `bifrost_types_macros::closing_account` (new published crate
  `crates/types-macros`) from the trait declaration. Every trait method carries
  an `#[admission(..)]` policy and a method without one fails to compile:
  - `#[admission(Operation)]`: provider call deferred into the returned
    future or stream; refused with `account_closed(Operation, protocol)` if the
    gate is closed at first poll. Borrowed arguments are cloned so the deferred
    call owns them; `self: Arc<Self>` methods forward to the provider's `Arc`,
    so provider defaults run against the provider, not the wrapper.
  - `#[admission(classify, Operation)]`: `inventory_resume_stream` only.
  - `#[admission(exempt)]`: forwarded; the return must implement the
    `Exempt` shape marker (shape check only, the annotation is the policy).
    Exempt: `protocol`, `capabilities`, `set_priority`, `set_bandwidth_cap`,
    `throttle_keys`, `describe_cursor`, `is_inventory_cursor`,
    `inventory_partitioning`, `flag_target`, `push_lanes`; generated as
    `ClosingAccount::EXEMPT_METHODS`.
  - `#[admission(close)]`: dedicated, see below.
- Admission is decided exactly once per future or stream, at the open-state
  check inside its first poll, and remembered: a call admitted while open and
  `Pending` at close stays admitted and keeps the provider's result, including
  any shutdown error the provider reports. A refused stream ends on one
  terminal item and never reports `Done`: `Terminated` for `SyncEvent`,
  `InventoryEvent`, `ScopeLifecycleEvent` and `InventoryRepairEvent` (the
  request stream is dropped unpolled, never drained), `Failed` for
  `PushSessionEvent`.
- Close: admission shuts synchronously when `close` is CALLED (a close future
  dropped unpolled still closes), then the provider's `close` is called
  synchronously and its future returned directly, on every call. The wrapper
  certifies admission closure only; awaiting `close` awaits that provider
  invocation.
- The `Account::close` trait doc states the post-close contract;
  `reference/error-model.md` `AccountClosed` points at it.

### Ruling: cursor classification after close (settled in link 1's spar)

The handed-back decision: `inventory_resume_stream`'s `Some`/`None` is how the
engine classifies a stored cursor, and `is_inventory_cursor` must agree with
it (fusion rejects disagreement). Candidates were: keep classification live
(A1); reshape to an always-stream resume plus a sole predicate (A2); return
`Some(refusal)` for every cursor after close (A3); make classification
fallible (A4).

Ruled A1. `is_inventory_cursor` and `inventory_partitioning` are exempt.
`inventory_resume_stream` calls the provider synchronously even after close,
keeps its `None`, and gates only the stream inside `Some` at first poll;
construction is not admission. A3 corrupts cursor identity and breaks the
checked equivalence; A2 reintroduces two separately maintained predicates,
which Graph's use of the default deliberately avoids; A4 infects the engine
for nothing. The contract is precisely: after close no provider work is
admitted and no inventory completion is claimed. It is NOT "every path
reaches a refusal": a stored ordinary cursor still classifies `None`, and
engine establishment installs it locally and returns `Ok` without polling a
gated method, as `run_resume_with_broadcast` returns `NoCursor`. Fencing a
local cursor install after close is the engine's lifecycle concern, not the
wrapper's, and changing classification is the wrong mechanism for it.

### Ruling: retain provider shutdown guards (link 2)

The wrapper covers new admission, not every later shutdown check. No existing
provider refusal was proven redundant across its whole use:

- IMAP send and draft guards run after acquiring the send lock, so close may
  win after wrapper admission; raw fetch checks run within admitted streams.
  Polling EXAMINE also serves the separately published `ImapPoller`, which is
  deliberately not an `Account` and cannot be covered by this wrapper.
- JMAP push registration checks closed under its subscription locks. Graph
  and Google push guards protect lease exchange, task and registration
  ownership, including work already admitted while open.
- Google's future adapter keeps both its initial shutdown check and its
  cancellation race. Close can occur between wrapper admission and the
  adapter's first poll; removing the initial check changes a local refusal
  into an ambiguous in-flight failure. Its stream adapter still governs
  admitted streams, which link 3 will address.

Retain these guards and their transport counterparts. An enterprise user
removing an account expects no late lease or send to escape teardown, and
expects an admitted write's actual transmission evidence to survive. This
link changes only the outer admission boundary, not admitted-work policy.
The hand-written calendar forwarder remains a provider implementation;
putting the gate in its test factory exercises provider overrides through
the same outer boundary as production factories.

## Link plan

Each link is one commit with its own gate.

1. Built: generator, `ClosingAccount`, admission at first poll, exemption
   list, trait doc contract, hermetic tests (`crates/types/src/closing_tests.rs`,
   ablation-checked). A method added without a policy is a macro compile error;
   no trybuild test pins that, since the workspace has no compile-fail
   harness.
2. Built: all six factories return `ClosingAccount::wrap(..)` outermost,
   including both IMAP `open` and `open_with_poller`. Provider references
   describe the shared `Account::close` contract. The calendar passthrough
   test factory now wraps its hand-written provider forwarder too; its
   provider overrides remain inside the gate. A hermetic regression checks
   that a calendar call constructed before close and one constructed after
   close both refuse without invoking the provider, even when the close
   future is dropped unpolled. Existing provider guards remain as ruled above.
   Validation results are recorded below. No implementation work remains for
   this link; the separate gate/commit agent owns the final workspace gate.
3. (Medium) Stream termination policy for ADMITTED streams per stream kind
   (drain or end when close lands mid-stream), with tests that a closed
   inventory stream never reports completion. Link 1 decides only refusal
   before admission.
4. (Small) IMAP: the pool's post-close `TransportFailure::Closed` stays as the
   second boundary but is no longer reachable from a gated method; pin that
   with a test through the wrapper.

Filed alongside, not part of this chain: whether concurrent `close` calls
share one teardown (Google returns `Ok` at once on a repeated close while the
first is still awaiting its watch teardown; Graph's `PushTasks::join` takes the
handles, so a concurrent close can finish without waiting). That is a provider
close-contract question; see `notes/todo.md`.

## Link 2 validation

- `brokkr test -p bifrost-sync calendar_factory_refuses_after_unpolled_close_without_forwarding --sweep workspace`
  passed. Removing only the calendar test factory's wrapper made that exact
  test fail: the preconstructed RSVP returned `Ok(())` after close. The
  wrapper was restored before the gate.
- `brokkr check -p bifrost-imap -p bifrost-jmap -p bifrost-graph -p bifrost-google -p bifrost-caldav -p bifrost-carddav -p bifrost-sync`
  passed: clippy and 14,959 tests across five sweeps, 1m53s total.
  This was deliberately package-scoped because other agents are editing the
  tree; final workspace validation and commit belong to the separate gate
  agent. `git diff --check` also passed.
- No decision handed back. Link 3 (medium) and link 4 (small) remain as listed;
  no extra implementation work was added to the plan.
